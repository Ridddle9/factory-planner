### `Справочник.РабочиеЦентры` ← БРИГАДЫ и ВРЦ (ОСНОВНОЙ ИСТОЧНИК)
**Иерархический справочник** — подтверждено через "Информация для технического специалиста":
форма называется `Справочник.РабочиеЦентры.Форма.СтруктураРабочихЦентров`.

Структура: папки (ЭтоГруппа=Истина) = цеха/участки, элементы = бригады/ВРЦ.
Цех берётся из `РЦ.Родитель.Наименование`.

Видимая структура (из формы "Структура рабочих центров"):
- **Цех изготовления потолочного профиля** (группа)
  - ВРЦ ГРИЛЬЯТО линия № 1, 2, 3, 4, 5
  - ВРЦ КУБОТА линия "CUBO", ВРЦ КУБОТА линия траверса
- **Цех металлообработки** (группа)
  - Станок SLIM с рольформой
- **Цех обработки и покраски алюминиевого профиля** (группа, пустая в скрине)
- **Цех пластиковых изделий** (группа)
  - ВРЦ Экструзия оптического рассеивателя
  - ВРЦ-1 Термопластавтомат 1000
- **Цех сборки светильников** (группа)
  - Бригада FLORA (4 чел), Бригада LEG-GR (5 чел)
  - Бригада № 1 (5 чел), Бригада № 1 сборки IP светильников (6 чел)
  - Бригада № 2 (5 чел), Бригада № 2 сборки IP светильников
  - Бригада № 3 (5 чел), Бригада № 3 сборки IP светильников
  - Бригада № 4 сборки IP светильников (4 чел)
  - Бригада круглых светильников (1чел)
  - Бригада сборки кольцевых светильников (дизайн)
  - Бригада сборки панелей, Бригада УНИВЕРСАЛ (9 человек)
  - Бригада упаковки (10 чел)
- **Цех электроники** (группа)
  - Бригада сборки источников питания
  - ВРЦ ВСЛ (Китай), ВРЦ ВСЛ (Тайвань)

Реквизиты: `Наименование`, `Родитель` (→ группа-цех), `ЭтоГруппа`, `ПометкаУдаления`
Другие реквизиты элемента: `ВидРабочегоЦентра`, `КоэффициентВремениРаботы`, `МаксимальнаяЗагрузка`, `Календарь`, `Описание`, `РасценкаРабота`, `РасценкаПереналадка`

## Регистры накопления

**Ключевые для синка заказов:**
- `ТоварыКОтгрузке` — товары обеспеченные/произведённые по заказу.
  - Измерения: `Склад`, `Получатель`, `ДокументОтгрузки`, `Номенклатура`, `Характеристика`, `Назначение` (`Справочник.СсылкаНазначения` — полиморфная), `Серия`
  - Ресурсы: `ВРезерве`, `КОтгрузке`, `КОформлению`, `КСборке`, `Собирается`, `Собрано`
  - Семантика: `КСборке` — запущено в сборку, `Собирается` — в процессе, `Собрано` — готово (на складе), `КОтгрузке` — ждёт отгрузки
  - Фильтр "нечего производить": `Собрано + КОтгрузке >= тов.Количество`
  - ⚠️ `ВЫРАЗИТЬ(Назначение КАК Документ.ЗаказКлиента)` — не работает, тип `СсылкаНазначения` несовместим. Прямой джойн по ЗаказКлиента невозможен через этот регистр.
- `УдалитьЗаказыКлиентов` — устаревший регистр остатков по заказам клиентов
- `ЗаказыНаСборку` — Измерения: `ЗаказНаСборку`, `Номенклатура`, `Характеристика`, `ТипСборки`, `КодСтроки`, `Серия`. Ресурсы: `Заказано`, `КОформлению`. ⚠️ Нет `ЗаказКлиента` — не подходит для фильтрации по заказу клиента.

### `РегистрНакопления.ВыпускПродукции`

- `Организация`, `АналитикаУчетаНоменклатуры`, `Распоряжение`

### `ГрафикПроизводстваПродукции` (расширение — источник capacity)

**Цель: тянуть `capacityPerDay` на уровне продукта (не категории) из этого расширения.**

**Регистры сведений:**
- `пк_Производительность` — **периодический** регистр (периодичность по позиции). Измерения: `ВидНоменклатуры` (тип `пк_ВидыНоменклатурыДляГрафикаПроизводства`); Ресурсы: `ПроизводительностьВСутки`. Записи хранят историю изменений capacity — у одного элемента могут быть пустые записи между заполненными. `СрезПоследних` даёт актуальное значение. Пример: "КОМПЛЕКТЫ ДЛЯ СВЕТИЛЬНИКОВ" = 500 ед/сутки с 29.11.2024.
- `пк_ПроизводительностьПоГруппамНоменклатуры` — то же самое, но по группам: измерение `ГруппаВидовНоменклатуры`; Ресурсы: `ПроизводительностьВСутки`

**Семантика мощности ✅ подтверждено:**
- `ПроизводительностьВСутки` — мощность **продуктовой линейки** (пк_-категории): FLORA = 150, LUM = 380 и т.д.
- Измерения бригады/РЦ в регистре нет и не планировалось
- Одна запись = сколько штук данной продуктовой линейки делается в сутки (суммарно, без разбивки по бригадам)

**Архитектурный вывод: capacity — на уровне продукта, не стандартной категории:**
- `пк_ВидыНоменклатурыДляГрафикаПроизводства` — это **продуктовые линейки**: "СВЕТИЛЬНИКИ FLORA", "СВЕТИЛЬНИКИ LUM", "КОРПУСА SLIM" и т.д.
- Стандартные `ВидыНоменклатуры` — это **типы спецификации**: "Тип I (плафон-размеры-IP-K-цвет)", "ЛВО-ЛПО" и т.д.
- Это **две разные классификационные оси** — названия не совпадают ✅ подтверждено
- Несколько пк_-линеек (FLORA 150, LUM 380) могут относиться к одному стандартному ВидНоменклатуры ("Тип I") — у каждой своя capacity
- Значит хранить capacity нужно на `Product`, не на `ProductCategory`

**Структура `пк_ВидыНоменклатурыДляГрафикаПроизводства` (подтверждена ✅):**
- Реквизиты: `Наименование`, `Родитель` (справочник **иерархический**)
- Поля `Спецификация` **нет** — мост через РесурсныеСпецификации неверен
- Вкладка "Производительность (по видам номенклатуры)" — связанный список из `пк_Производительность`
- Наименование содержит capacity в скобках: "СВЕТИЛЬНИКИ LUM (380 max)" — это просто текст для читаемости, не отдельное поле
- Есть группа "СВЕТИЛЬНИКИ" (~30 элементов) + ~18 элементов без группы (ГРИЛЬЯТО GL15, ПОТОЛКИ CLIP-IN, УГОЛОК и т.д.)
- Diapason capacity: от 15 (РЕЦИРКУЛЯТОРЫ) до 35000 (ПОТОЛОЧНЫЙ ПРОФИЛЬ ГРИЛЬЯТО)
- Capacity в базовой конфигурации 1С **отсутствует** — только в этом расширении. Raytec тоже не использует (Finite=0, независимые системы).

**Мост — capacity per product code ✅:**
```
пк_Производительность.ВидНоменклатуры (пк_-тип)
  ← JOIN ← Справочник.Номенклатура.пк_ВидДляРасчетаГрафикаПроизводства
  → Номенклатура.Код  ← по этому полю матчим с нашим Product.code
  → Произв.ПроизводительностьВСутки
```

**Итоговый BSL-запрос (capacity per product code):**
```sql
ВЫБРАТЬ
    Ном.Код КАК КодНоменклатуры,
    Произв.ПроизводительностьВСутки КАК ПроизводительностьВСутки
ИЗ Справочник.Номенклатура КАК Ном
    ВНУТРЕННЕЕ СОЕДИНЕНИЕ РегистрСведений.пк_Производительность.СрезПоследних КАК Произв
    ПО Произв.ВидНоменклатуры = Ном.пк_ВидДляРасчетаГрафикаПроизводства
ГДЕ НЕ Ном.ПометкаУдаления
    И ЗначениеЗаполнено(Ном.пк_ВидДляРасчетаГрафикаПроизводства)
```

**Общие модули — `пк_ГрафикПроизводстваПродукцииРасчетСервер` (полный список функций):**

`ПолучитьТаблицуПроизводительности(ДатаПотребности, ВидНоменклатуры)`:
- Читает `пк_Производительность.СрезПоследних(&Период, ВидНоменклатуры = &ВидНоменклатуры)`
- **Возвращает ЧИСЛО** (`ПроизводительностьВСутки`), не таблицу! Название функции вводит в заблуждение.
- Возвращает `Неопределено` если запись не найдена

`ПолучитьТаблицуПроизводительностиПоГруппе(ДатаПотребности, ГруппаВидовНоменклатуры)`:
- То же самое, но из `пк_ПроизводительностьПоГруппамНоменклатуры.СрезПоследних`
- Возвращает ЧИСЛО

`ПолучитьРабочиеДниОсновногоКалендаря(НачалоОтсчета)` Экспорт:
- Читает `РегистрСведений.КалендарныеГрафики` где `ДеньВключенВГрафик = Истина`
- Параметр `Календарь = Константы.ОсновнойКалендарьПредприятия.Получить()`
- Возвращает массив дат

`ПолучитьСледующийРабочийДеньНаДату(ДатаОтсчета)` Экспорт:
- `ВЫБРАТЬ ПЕРВЫЕ 1` из `КалендарныеГрафики` где дата > ДатаОтсчета и `ДеньВключенВГрафик`
- Возвращает дату или `Неопределено` (если ДатаОтсчета = Дата(1,1,1))

`ОтобратьСтрокиПоКритериям(Источник, СтруктураКритериев, СтруктураСложныхКритериев)` Экспорт:
- Утилита фильтрации через `ПостроительЗапроса`

`ПолучитьПотребностиПоЗаказамКлиентов()` Экспорт:
- Читает из регистра остатков и доступности (не напрямую из `ЗаказКлиента.Товары`)
- Фильтр: `ТипЗаписи` IN {"Не обеспечено", "Ожидается", "Сейчас"} + условия на резерв/обеспечение
- Учитывает `ЗаказНаПеремещение` в дополнение к `ЗаказКлиента`
- Ключевые строки заполнения:
  ```bsl
  НоваяСтрока.ВидНоменклатуры = СтрокаОстатков.Номенклатура.пк_ВидДляРасчетаГрафикаПроизводства;
  НоваяСтрока.ВидНоменклатурыТиповой = СтрокаОстатков.Номенклатура.ВидНоменклатуры;
  ```
- Колонки результата: `ЗаказКлиента`, `Номенклатура`, `Характеристика`, `ВидНоменклатуры` (пк_ тип), `ВидНоменклатурыТиповой` (стандартный), `Код`, `Потребность`, `ВПроизводстве`, `Остаток`, `ДатаОтгрузки`, `ДатаОтгрузкиПлановая`, `ВРезерве`, `КОбеспечению`, `Доступно`, `Приоритет`, `ПриоритетПоДате`, `ДатаЗаказа`, `Запланировано`, `ВыпускЗапланирован`

`Трофимов_РассчитатьГрафикПроизводстваПродукции()` Экспорт (упрощённая версия):
- Итерирует потребности, для каждой — по дням начиная с завтра
- На каждый день вызывает `ПолучитьТаблицуПроизводительности(ДатаВыпуска, СтрокаПотребности.ВидНоменклатуры)`
- Без учёта рабочего календаря

`РассчитатьГрафикПроизводстваПродукции(ТаблицаПотребностейПоЗаказамКлиентов)` (версия Сиротин):
- Итерирует по рабочим дням из `ПолучитьРабочиеДниОсновногоКалендаря`
- На каждый день проверяет ДВА ограничения: по категории И по группе категорий
- `ВозможныйВыпуск = Мин(ОстатокПоПроизводительностиПоГруппе, ОстатокПоПроизводительности)`
- Если производительность не найдена → `Прервать` с сообщением об ошибке
- Есть закомментированная константа `МаксимальнаяПроизводительностьПоНоменклатуре`

**Ключевые решения (июль 2026):**
✅ `з.Ссылка.УникальныйИдентификатор()` — GUID документа как уникальный ключ вместо `Номер`.

### Детали ключевых функций

**`МассивНоменклатурыДляВыгрузки`** — фильтр номенклатуры для Raytec:
- Источник: `Справочник.Номенклатура.ДополнительныеРеквизиты` по свойству "Группа учета продаж"
- Значение из константы Raytec: `рткКонстанты.ЗначениеКонстанты("ГруппаУчетаПродажВыгружаемойНоменклатуры")`
- ⚠️ Не все позиции — только с заполненным доп. реквизитом

**`ДанныеТаблицы_RealData_ResourceData`**:
- ID = UID(`ВТ_РесурсныеСпецификации.ВидРабочегоЦентра.Ссылка`), Name = Наименование
- **`Finite = 0`** — все ресурсы передаются в Raytec как **бесконечные**
- `МаксимальнаяЗагрузка` НЕ используется

**`ТекстЗапросаВторичныеОграничения`** — **ПОЛНОСТЬЮ закомментирована**:
- Должна была передавать `МаксимальнаяЗагрузка` как вторичное ограничение
- Читала `ВидыРабочихЦентров.МаксимальнаяЗагрузка` (для ВРЦ без РЦ с `ПараллельнаяЗагрузка=Истина`)
- И `РабочиеЦентры.МаксимальнаяЗагрузка` (для РЦ с `ВидРЦ.ПараллельнаяЗагрузка=Истина`)
- Функция возвращает пустую строку — фича отключена намеренно, Raytec работает без ограничений

**`ДанныеТаблицы_RealData_RoutingData`**:
- Конвертирует `ЭтапыПроизводства.ВремяРаботы` из разных единиц → минуты
- Делитель: `ЗагрузкаВРЦ * КоличествоРабочихЦентров * КоличествоУпаковок`
- `МаксимальнаяЗагрузка` не используется

**`ДанныеТаблицы_RealData_Demand`** (полные фильтры подтверждены из кода):
- Первый шаг: `МассивНоменклатурыДляВыгрузки()` → только номенклатура с "Группа учета продаж"
- `ТекстЗапросаРесурсныеСпецификацииИРесурсы()` строит `ВТ_РесурсныеСпецификации` только для этих позиций
- Источник: `РегистрСведений.РаспределениеЗапасов` + **ВНУТРЕННЕЕ СОЕДИНЕНИЕ** `ВТ_РесурсныеСпецификации` — позиции без "Группа учета продаж" не попадают вообще
- LEFT JOIN `ЗаказКлиента.Товары` по {Ссылка, Номенклатура, Характеристика}
- Фильтр Состояние: `Обеспечить | ОбеспеченКДате | ОжидаетсяПоНеподтвержденномуЗаказу`
- Фильтр ВариантОбеспечения: NOT IN {Отгрузить, СоСклада, НеТребуется, ПереданРанее}
- Фильтр кол-во: `Обеспечено + НеОбеспечено > 0`
- Склады: из константы `СкладыВыгружаемыхЗаказов`
- **DueDate = `ЗаказКлиентаТовары.рткДатаПередачи`** (per-row, не per-order); если NULL/пусто → `ТекущаяДата`
- Priority: `ЗаказКлиента.Приоритет` → 10/20/30/40 (40 если не задан)
- ⚠️ Фильтра по `ДатаОтгрузки` **нет** — подтверждено кодом
- ⚠️ Причина отсутствия заказов на ИСТОЧНИКИ ПИТАНИЯ (001579, 002835, 005698): продукты ЦБ-00007142, ЦБ-00010106 не имеют "Группа учета продаж" → исключены через INNER JOIN

**`ЗагрузитьЗаказыПроизводственногоРасписанияНаСервере`**:
- Читает `RealData_Schedule` из Raytec DB (внешний источник данных `риаRaytecAPS`)
- Resource_ID (GUID) → маппит в `Справочник.РабочиеЦентры` (не `ВидыРабочихЦентров`!)
- Route_ID → `Справочник.РесурсныеСпецификации`
- Пишет в `РегистрСведений.риаПроизводственноеРасписание`

### `capacityPerTeamPerDay` — финальный вывод

`МаксимальнаяЗагрузка` **существует** в обоих справочниках (`ВидыРабочихЦентров` и `РабочиеЦентры`). Raytec написал под него код (`ТекстЗапросаВторичныеОграничения`), но **отключил** — все ресурсы идут с `Finite=0`. Заполнен ли реквизит реальными данными — не проверялось.

**Вывод:** источника нет, вводить вручную в UI.
