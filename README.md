# Фабрика (Factory Planner) — планирование производства

B2B SaaS-приложение для планирования производства. Несколько компаний, каждая со своими данными.

**Содержание:** [Контекст](#контекст-и-цели) · [Модель данных](#модель-данных) · [Сравнение с Raytec](#сравнение-с-raytec) · [Разработка](#разработка) · [Деплой](#деплой) · [API](#api) · [Интеграция с 1С](#интеграция-с-1с) · [История изменений](#история-изменений)

## Контекст и цели

**Задача:** заменить ручной обмен Excel-файлами между офисом и производством на единую веб-систему.

**Пользователи:**
- **Руководитель (ADMIN)** — первый зарегистрированный в компании пользователь. Подтверждает заявки коллег на доступ, управляет токеном синхронизации с 1С.
- **Планировщик** — загрузка заказов из 1С, формирование и корректировка плана, сводка факта.
- **Начальник цеха** — распределение бригад, ввод фактического выпуска и комментариев.

**Проблемы текущего процесса:** ручной обмен файлами, риск рассинхронизации, дублирование данных, нет единого источника правды.

## Модель данных

| Сущность | Описание |
|----------|----------|
| **Company** | Компания: ИНН, название, `syncToken` (токен для 1С). Единица изоляции данных. |
| **User** | Пользователь: email, пароль (bcrypt), роль (ADMIN/MEMBER), статус (PENDING/APPROVED/REJECTED). |
| **Workshop** | Участок/цех. Группировка категорий. |
| **ProductCategory** | Категория номенклатуры (= производственная группа из ДопРекв 1С). `capacityPerTeamPerDay` — фолбэк мощности; обычно 0, мощность хранится на уровне продукта. |
| **Product** | Номенклатура: код (= `Артикул` из 1С), название, категория, мощность-фолбэк (`capacityPerDay`), флаг ручной блокировки (`capacityLocked`). `kind`: `product` или `component` — своя комплектующая (полуфабрикат), заведённая синком из состава изделий. |
| **BomLine** | Строка состава изделия из 1С (`РесурсныеСпецификации.МатериалыИУслуги`): материал, ед. изм., вид номенклатуры, производственная группа, расход на 1 шт (`qtyPerUnit`). `componentProductId` — ссылка на свою комплектующую (`Product`), у покупных пусто. Хозяин — 1С: синк заменяет состав компании целиком. |
| **ProductTeamCapacity** | Мощность номенклатуры для конкретной бригады (шт/чел/день, `Float` — «Загрузка» в 1С бывает дробной). Уникальный ключ `[productId, teamId, companyId]`. Если у товара есть такие записи, он планируется только на эти бригады. |
| **Team** | Бригада. `headcount Int @default(1)` — количество людей (из `КоличествоРабочихЦентров` в 1С, обновляется при синке). Привязывается к категориям через CategoryTeam. |
| **TeamDayCapacity** | Корректировка мощности бригады на конкретный день (фактор 0.0–1.0, причина). |
| **Order** | Заказ клиента: GUID из 1С (`orderRef`), номер (для отображения), клиент, срок, менеджер, флаг `active`. |
| **OrderItem** | Позиция заказа: товар, количество К (к обеспечению). |
| **DailyTask** | Задача на день: позиция + дата + план + факт + комментарий. `loadShare` — доля бригадо-дня, которую задача занимает по плану (ставит планировщик, сбрасывается при ручной правке количества или бригады). Флаг `manuallyPlaced` защищает ручные переносы от автоматических каскадов. |
| **CategoryBlock** | Блокировка производства категории на период (нет запчастей, плановый простой). |

### Мультитенантность

Каждая компания полностью изолирована. `Workshop`, `ProductCategory`, `Team`, `Product`, `Order` имеют `companyId`. Уникальные ключи составные: `[name, companyId]`, `[code, companyId]`, `[orderRef, companyId]`. Авторизованные запросы автоматически фильтруются по компании текущего пользователя.

### Ключевые связи

- `Company` → `User[]`, `Workshop[]`, `Team[]`, `ProductCategory[]`, `Product[]`, `Order[]`
- `ProductCategory` ↔ `Team` — many-to-many через `CategoryTeam`
- `Product` → `ProductTeamCapacity[]` (мощность по бригадам)
- `Product` → `BomLine[]` (состав); `BomLine.componentProductId` → `Product` (своя комплектующая, где используется — `usedIn`)
- `Team` → `ProductTeamCapacity[]`
- `Order` → `OrderItem[]`
- `OrderItem` → `DailyTask[]`
- `DailyTask` → `OrderItem`, `Team`, дата
- `Team` → `TeamDayCapacity[]`

### Модель нагрузки бригады

Нагрузка считается в долях бригадо-дня: `load = Σ доля задачи` по всем задачам бригады за день. Доля задачи — `DailyTask.loadShare`, если задачу ставил планировщик, иначе `plannedQuantity / (capacityPerDay × team.headcount)`.

- `load = 1.0` — полный рабочий день
- `load > 1.0` — перегруз
- `TeamDayCapacity.factor` — доступная доля дня (например, `0.7` = вышло 7 из 10 человек)

Мощность на одного человека в день определяется по цепочке приоритетов:

1. **`ProductTeamCapacity.capacityPerDay`** — мощность конкретной пары (продукт, бригада), дробная. Заполняется при синке из `ПолучитьCapacity()`: BSL берёт `Загрузка` из `ЭтапыПроизводства.ВидыРабочихЦентров` + `АльтернативныеВидыРабочихЦентров`, возвращает один элемент на каждую пару (Артикул, бригада). Разные бригады могут иметь разную мощность для одного продукта. **Если у товара есть хотя бы одна такая запись, кандидаты — только бригады с записью**, категория не используется.
2. **`Product.capacityPerDay`** — глобальный фолбэк на продукт, только для товаров без записей по бригадам (тогда кандидаты — бригады категории). Защищается флагом `capacityLocked = true` — при включённой блокировке синк не перезаписывает значение.
3. **`ProductCategory.capacityPerTeamPerDay`** — фолбэк на категорию (ручной ввод в UI).

Реальная ёмкость бригады за день = `capPerPerson × team.headcount`.

`Product.capacityLocked = true` — только `capacityPerDay` защищён от перезаписи; `ProductTeamCapacity` при этом продолжает обновляться из синка.

**Деление позиции по дням (как у Raytec):** время бригады непрерывное, позиция занимает `Q / мощность` бригадо-дней. В каждый день — целая часть штук, остаток от округлений — в последний день позиции (22,5 шт/день, 61 шт → 22, 22, 17).

## Сравнение с Raytec

Raytec APS — планировщик, с которым сверяется заказчик. Его алгоритм восстановлен по планам от 16.10 и 23.10 и коду выгрузки из 1С; правила и доказательства — в [`docs/1c_map.md`](docs/1c_map.md), раздел «Алгоритм планирования Raytec». На плане 23.10 модель с порядком очереди Raytec совпадает со всеми позициями на 100%.

**Уже как у Raytec:** деление по дням с непрерывным временем, дробные нормы, бригады только с нормой на товар, только активные заказы в «Перепланировать очередь», позиция целиком на одной бригаде — той, что раньше освободится.

**Решения по расхождениям (26.10.2026):**

| Тема | У нас | У Raytec | Решение | Статус |
|------|-------|----------|---------|--------|
| Норма альтернативных бригад | своя у каждой бригады (из 1С) | норма основного РЦ × своя численность | **оставляем как у нас** | — |
| Выбор бригады | позиция целиком на бригаду, которая раньше освободится; ручные задачи учитываются (см. «Ручные правки») | позиция целиком на бригаду, которая раньше освободится | **как у Raytec** | ✅ сделано |
| Дата передачи | минимальная по заказу | своя у каждой строки (`МАКСИМУМ` по строкам товара) | **как у Raytec**: 1С — дата по строке, бэк — очередь по ней | ⏳ бэк готов (`OrderItem.transferDate`), ждёт загрузки `ПолучитьЗаказы()` вариант В |
| Какие заявки планировать | все из `ПолучитьЗаказы()` | без «Резервировать на складе», «Не обеспечивать», «Излишек»; только склады из `СкладыВыгружаемыхЗаказов` | **как у Raytec**, кроме «Группы учета продаж» (иначе пропадут ГРИЛЬЯТО, GL15, КУБОТА) | ⏳ BSL написан и сверен с кодом Raytec (`docs/1c_map.md`, вариант В), ждёт загрузки в 1С |
| Приоритет в очереди | приоритет → Дата передачи → согласование | не используется | **оставляем как у нас** (на проде «Высокий» у 4 заказов из 253) | — |
| Порядок при одинаковой Дате передачи | дата согласования | по UID номенклатуры | **пока не меняем** | отложено |
| Праздники | 04.11 и 1–8 января — выходные | рабочие | **оставляем как у нас** | — |

На копии прода от 25.10 против плана Raytec от 23.10 (372 общие позиции) смена выбора бригады дала: бригада совпала 62% → 66%, окончание день в день 31% → 36%, позиций, разъехавшихся по нескольким бригадам, 45 → 0. Основное оставшееся расхождение — нормы альтернативных бригад (решено оставить свои).

Совпасть с Raytec 1 в 1 полностью не получится и не нужно: мы сознательно учитываем праздники и ручные правки мастеров (Raytec каждый раз считает с нуля).


### Nginx (правильная конфигурация для SPA + API)

⚠️ **Важно:** нельзя проксировать всё на Express. React-роуты (`/workshops`, `/orders` и т.д.) совпадают с API-роутами Express — nginx должен раздавать SPA статику сам, а в Express пускать только API.

```nginx
server {
    listen 80;
    server_name _;

    # /sync/, /auth/, /admin/, /import/ — напрямую в Express
    location ~ ^/(sync|auth|admin|import)/ {
        proxy_pass http://localhost:3000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        client_max_body_size 50m;
    }

    # /api/* — стрипаем /api/ и пускаем в Express (как делал Vite proxy в dev)
    location /api/ {
        proxy_pass http://localhost:3000/;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        client_max_body_size 50m;
    }

    # Всё остальное — SPA из frontend/dist
    location / {
        root /home/ridddle/factory-planner/frontend/dist;
        try_files $uri /index.html;
    }
}
```

```bash
sudo tee /etc/nginx/sites-available/factory-planner > /dev/null << 'EOF'
# (вставить конфиг выше)
EOF
sudo ln -s /etc/nginx/sites-available/factory-planner /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx
```

⚠️ **После каждого `npm run build`** — nginx должен иметь доступ к файлам:
```bash
chmod o+x /home/ridddle
chmod -R o+r /home/ridddle/factory-planner/frontend/dist
```
Без этого nginx падает с `Permission denied (13)` и возвращает 500.

## Авторизация

- Первый зарегистрировавшийся пользователь в компании (по ИНН) получает роль **ADMIN** и сразу входит.
- Последующие регистрации создают заявку **PENDING** — ADMIN видит их на странице «Администрирование» и подтверждает.
- Данные **полностью изолированы** по компании. Пользователь другой компании не видит ни заказов, ни бригад, ни графика чужой компании.
- Сессия — `httpOnly` cookie (JWT, срок 30 дней).

### Справочники

- **Участки** — добавить, изменить, скрыть, удалить. Вкладка «Скрытые» — восстановление. Скрытый участок пропадает отовсюду вместе с категориями, а синк из 1С и планирование продолжаются. Участок с категориями удалить нельзя — окно предлагает скрыть.
- **Категории** — то же самое (вкладка «Скрытые», удаление категории с товарами не даёт и предлагает скрыть); кнопка «Бригады» — привязка бригад к категории; «Блоки» — блокировки производства на период.
- **Товары** — номенклатура; поиск по коду и названию, фильтр по категории.
- **Бригады** — две вкладки:
  - **Список бригад** — название и численность.
  - **Мощности по дням** — сетка-календарь; «Добавить корректировку» или клик по клетке открывает форму над сеткой: бригада, период «с … по …», мощность в % (можно больше 100% — сверхурочные), причина. Выходные и праздники в период не входят. Активные корректировки — списком периодов.

### Заказы

Две вкладки — **Актуальные** и **Архив** — и поиск по номеру, клиенту, менеджеру и товару. Колонка «Готово по плану» — прогноз по текущим задачам. В карточке заказа — позиции с датой передачи, «Автоплан» позиции и заказа, «Перепланировать заказ» и «Информация для производства» из 1С.

### График (главный экран работы)

Сетка: строки — позиции заказов (сгруппированы по участку и бригаде), колонки — дни. Шапка и первые колонки закреплены, нерабочие дни серые, в шапке дня — полоска загрузки. На телефоне — вид «День» (задачи выбранного дня) и «Таблица».

**Ячейка → окно задачи:**

| Действие | Что делает |
|---|---|
| Количество → «Сохранить» | Меняет план на день; правка закрепляется (значок булавки, автоматика её не трогает) |
| «Перенести…» | Окно переноса: дата, бригада (сверху — с нормой на товар), загрузка бригады в этот день. «Освободившееся место»: **Заполнить** (следующие задачи бригады сдвигаются раньше) или **Оставить пустым** (остальные остаются на своих днях; в ячейке пишется «оставлено пустым»). Галочка «Перенести позицию целиком — все дни» |
| «Разбить» | Часть количества — на другой день |
| «Удалить» | Снимает задачу с графика; галочка «Удалить позицию целиком — все дни». Снятое попадает в «Не в графике» и автоматикой обратно не ставится |
| «Снять закрепление» | Ручная правка снова в руках автопланирования; при наведении на булавку — кто и когда закрепил |

После переноса окно показывает, что сдвинулось и что встало на освободившееся место. «Отменить» — для последнего действия (после возврата в график и переноса позиции целиком — точный откат по снимку плана).

**Кнопки:**

| Кнопка | Действие |
|---|---|
| **Скачать Excel** | Выгрузка плана за период — формат `Эксели с датами/export_to_be.xlsx` |
| **Запланировать незапланированные** | Планирует недостающее количество позиций по очереди (снятое вручную не трогает) |
| **Перенести недодел со вчера** | Невыполненное вчера — на ближайшие дни |
| **Перепланировать очередь** | Пересобирает весь незапущенный план по очереди (ручные правки и факт остаются) |
| **Категории без бригад** | Список категорий без бригады с назначением прямо здесь |
| **Не в графике** | Позиции, у которых часть количества не стоит в плане, с причиной; «Вернуть в график» — в очередь (FIFO) или с даты |
| **Реестр переносов** | Кто, что, откуда и куда переносил, снимал с графика и возвращал; отменённое помечено |
| **Очистить график** | Удаляет план; факт остаётся |

### Перепланирование при переносе

**Очередь** — приоритет заказа → Дата передачи строки (`рткДатаПередачи` из 1С) → дата согласования. Бригада одна на позицию — та, что раньше освободится.

При переносе задачи (другая дата или бригада) план затронутых бригад пересобирается планировщиком (`replanTeamFrom`): автоматические задачи с самого раннего затронутого дня удаляются и ставятся заново по очереди на ту же бригаду — лишнее в новом дне уходит дальше, без пробелов и без удлинения очереди. В режиме «Оставить пустым» старая бригада не трогается, а новая пересобирается с нового дня так, что ни одна позиция не встаёт раньше своего дня (`keepStarts`) — задачи только сдвигаются вправо.

**Ручные правки неприкосновенны:** задачи с `manuallyPlaced = true` (перенос, правка количества или бригады, добавленная вручную, разбивка) автоматика не двигает и не удаляет; остаток позиции планируется вокруг них. Факт (`actualQuantity`) не удаляется никогда.

### Реестр переносов

Кнопка «Реестр переносов» в «Графике» (в «Действиях», рядом с «Не в графике») открывает под панелью список ручных изменений графика: **что** (заказ, клиент, товар, штуки, дни), **откуда** (даты и бригада), **куда**, **кем** и **когда**. Записываются: перенос задачи, перенос позиции целиком, разбивка, снятие с графика (одной задачи и всей позиции) и возврат в график (в очередь или с даты). Для переноса видно, заполнили освободившееся место или оставили пустым.

Вкладки «Все / Переносы / Снято с графика / Возвраты», период (по умолчанию 30 дней), поиск по заказу, клиенту и товару, фильтр по сотруднику. Если действие отменили кнопкой «Отменить», строка остаётся, но помечается «отменено» (кем и когда) и номер заказа зачёркивается. Номер заказа, товар и бригады сохраняются в записи текстом — строка не пропадает, даже если заказ потом закрыли в 1С. Автоматические сдвиги (пересборка очереди после переноса) в реестр не пишутся — только действия людей.

### Блокировки категорий

Когда производство категории невозможно на период (нет запчастей, плановый простой, отпуск цеха) — создаётся `CategoryBlock`.

- **Планировщик автоматически пропускает заблокированные даты** — `autoPlanOrderItem` обходит даты, попадающие в любой активный блок категории.
- **Каскад при создании блока** — опция «Перераспределить задачи из периода» (`cascadeTasks=true`): задачи из периода блокировки удаляются и складываются на первый рабочий день после конца блока, после чего запускается `cascadeShiftRight` чтобы разрядить перегруз.
- **UI** — на странице «Категории» кнопка «Блоки» открывает модальное окно со списком активных блоков (чипы: период + причина) и формой создания нового блока (даты, причина, чекбокс каскада). Снять блок можно кнопкой «Снять» на каждом чипе.

### Страница «Товары»

- **Колонка «Произв. на чел./день»** — если для продукта есть данные по бригадам из 1С, отображается кнопка **«Смотреть»**; при клике открывается модальное окно с таблицей «Бригада → производительность на чел./день». Если данных по бригадам нет — показывается глобальное число `capacityPerDay` (с иконкой 🔒 если ручная блокировка).
- **Редактирование производительности** — поле в форме «Изменить» задаёт глобальный фолбэк `Product.capacityPerDay`; при сохранении ненулевого значения автоматически выставляется `capacityLocked=true`
- **Кнопка «Сбросить»** — снимает `capacityLocked`; следующий синк с 1С перепишет глобальное значение
- **Поиск** — фильтрация по коду или названию прямо в таблице

### Аналитика и планирование

Вкладки страницы «Аналитика»:

- **Загрузка бригад** — все бригады × дни: доля рабочего дня, занятая планом (с учётом корректировок мощности), средняя за период. Переключатели «Все бригады / Перегрузка / Недогрузка». Клик по бригаде — её позиции по дням; «← назад» возвращает к предыдущему виду
- **Завершение заказов** — скрыта в интерфейсе (эндпоинт `/planning/orders-completion` остался)
- **Факт за день** — сводка выпуска по бригадам и категориям за выбранный день
- **Незапланированный факт** — позиции, по которым зафиксирован выпуск без плана

### Администрирование (только ADMIN)

Страница `/admin/approvals`. Два блока:

**Синхронизация с 1С** — токен компании для расширения 1С. Кнопки: Показать / Скрыть, Скопировать, Перегенерировать (инвалидирует старый токен).

**Заявки на доступ** — список пользователей со статусом PENDING, кнопки «Разрешить» / «Отклонить».

## Интеграция с 1С

**Платформа:** 1С:ERP Управление предприятием 2, версия 8.3.27.1936

### Стратегия

- Расширение 1С (`ФабрикаПланнер`) **push-ит данные** на `POST /sync/1c`
- Аутентификация — Bearer-токен компании: `Authorization: Bearer <syncToken>`
- Токен хранится в БД (`Company.syncToken`), генерируется при регистрации компании
- ADMIN видит и копирует токен на странице **«Администрирование»** → «Синхронизация с 1С»

### Настройка интеграции (пошагово)

1. Зарегистрировать компанию и войти как ADMIN
2. Перейти в **Администрирование** → нажать «Показать» → скопировать токен
3. Открыть в 1С расширение **ФабрикаПланнер** → Настройки → вставить токен в поле «Токен»
4. Нажать кнопку «Отправить в Factory Planner» — данные синхронизируются

При компрометации токена — нажать «Перегенерировать» и обновить настройки в 1С.

### Что синхронизируется

| Данные | Источник в 1С | Частота |
|--------|--------------|---------|
| Заказы + номенклатура | `ЗаказКлиента`, таб. часть `Товары` | Ежедневно |
| Категории | `Справочник.Номенклатура.ДополнительныеРеквизиты`, свойство **"Производственная группа"** | Ежедневно |
| К обеспечению | `РегистрСведений.РаспределениеЗапасов` (СостояниеЗапаса IN НеОбеспечен, ОжидаетсяКПоступлению, НаСогласованииПоставки) | Ежедневно |
| Факт выпуска | `РаспределениеЗапасов` (delta НеОбеспечен: prev − curr); дельта считается на бэкенде | Ежедневно |
| Бригада → категория | `РесурсныеСпецификации.ОсновноеИзделиеЭтап` → `ЭтапыПроизводства.ВидыРабочихЦентров` + `АльтернативныеВидыРабочихЦентров` + доп. реквизит "Производственная группа" | Ежедневно |
| Мощность по бригадам + номенклатура | `ЭтапыПроизводства.ВидыРабочихЦентров.Загрузка` (основные) + `АльтернативныеВидыРабочихЦентров.Загрузка`; один элемент на каждую пару (Артикул, бригада); пишется в `ProductTeamCapacity`; продукты создаются из этого источника даже без активных заказов | Ежедневно |

## История изменений

### [текущая] — ноябрь 2026

#### Состав изделий из 1С (основа сквозного планирования)

- `POST /sync/1c` принимает `materials` — состав изделий из `РесурсныеСпецификации.МатериалыИУслуги` (BSL `ПолучитьМатериалы()`, см. `docs/1c_map.md`). Новая таблица `BomLine` хранит расход на 1 шт: спецификация бывает на 60 или 100000 изделий, количество делится на `ОсновноеИзделиеКоличествоУпаковок`.
- Свои комплектующие отличаются видом номенклатуры «Полуфабрикат» и заводятся как обычные товары (`Product.kind = "component"`) в категории по своей «Производственной группе» (или «Комплектующие без группы»). Так их потом можно ставить в график тем же планировщиком: бригады, нормы и партии задаются у товара, состав остаётся за 1С.
- Комплектующие заводятся до разбора строк, поэтому многоуровневый состав (линейка со своей спецификацией внутри светильника) собирается за один синк, и повторный синк ничего не добавляет.
- Если у изделия две спецификации с одной датой, берётся первая — строки второй пропускаются, а не складываются.
- `GET /bom?productId=` — состав изделия, `GET /bom/components` — свои комплектующие с признаком «настроено» (есть бригады и норма).
- В лог синка вместо всего состава пишутся первые 5 строк.
- Полный состав — около 140 тыс. строк, 50–80 МБ: лимит тела запроса для `/sync/1c` поднят до 200 МБ (Express — только этот маршрут, остальным 50 МБ; nginx — блок `/sync|auth|admin|import`). BSL пишет JSON без переносов строк (`ПараметрыЗаписиJSON(ПереносСтрокJSON.Нет)`) и шлёт только нужные поля.

#### Реестр переносов

- Новая таблица `PlanMove`: каждое ручное изменение графика (перенос, перенос позиции целиком, разбивка, снятие с графика, возврат) пишется с автором, временем, откуда/куда и режимом («заполнить» / «оставить пустым», FIFO / с даты). Запись делает сервер в тех же запросах (`PUT/DELETE /daily-tasks/:id`, `POST /daily-tasks/:id/split`, `POST /order-items/:id/return`), поэтому попадают переносы и из «Графика», и из «Плана на день».
- «Отменить» не создаёт встречную запись, а помечает исходную отменённой: по `undoOf` (снятие, перенос задачи с фактом) или по снимку плана (`snapshotId` — перенос, перенос позиции целиком, возврат).
- «Отменить» переноса одной задачи (и смены бригады в окне задачи) теперь тоже работает через снимок плана. Раньше это был обратный перенос по id задачи: он молча не срабатывал, если задача влилась в автоматическую задачу позиции (после пересборки бригады у неё новый id), а при вливании в закреплённую задачу уносил назад всё её количество. Задача с фактом отменяется по-старому — факт в снимок не входит.
- Кнопка «Реестр переносов» в «Графике» рядом с «Не в графике» раскрывает панель с вкладками по типу, периодом, поиском и фильтром по сотруднику; список обновляется после каждого изменения графика, на телефоне строки складываются в карточки.

#### Скрытие участков

- Участки скрываются так же, как категории: на странице «Участки» кнопка «Скрыть», вкладка «Скрытые» с кнопкой «Восстановить» (`PUT /workshops/:id` с `visible`, `GET /workshops?hidden=1`). Видна колонка «Категорий».
- Скрытый участок пропадает из интерфейса вместе со своими категориями: график, заказы (позиции), товары, категории, «Не в графике», аналитика, выгрузка в Excel, помощник; бригады, занятые только скрытым, тоже не показываются. Категория видна, только если видна она сама и её участок (`VISIBLE_PRODUCT`, `CAT_VISIBILITY` / `catVisible`).
- Синк из 1С по-прежнему сохраняет заказы и товары скрытого участка, а сам участок остаётся скрытым (upsert участка видимость не меняет). Планировщик позиции скрытых участков планирует, загрузка бригад их учитывает («Запланировать незапланированные» раньше пропускал скрытые участки — исправлено).
- Удалить участок, в котором есть категории, нельзя (раньше категории удалялись каскадом): окно объясняет и предлагает скрыть участок; если участок приходит синком из 1С, лучше скрыть, чем удалять.

#### «Не в графике»: снятые с графика позиции, удаление и перенос позиции целиком

- **Снятое вручную помнится.** Удаление задачи из «Графика» записывает у позиции `OrderItem.offPlanQty` (+ `offPlanAt`, `offPlanBy`, `offPlanTeamId`). Автоматика это количество обратно не ставит: `autoPlanOrderItem` вычитает его (`offPlanHold` — не больше, чем реально не стоит в плане), «Запланировать незапланированные», «Перепланировать очередь» и пересборки при переносах снятое не возвращают. Явное «Автоплан» позиции или заказа в карточке заказа и «Вернуть в график» снимают отметку. Задача, добавленная руками, уменьшает снятое на своё количество.
- **Список «Не в графике»** (кнопка с числом позиций в «Графике», `GET /order-items/off-schedule`): позиции активных заказов, у которых часть количества (количество из 1С минус план без факта) не стоит в плане. Причина: «Снято вручную · кто · когда · бригада», «Нет бригады с нормой», «Не запланировано». Порядок — очередь планировщика. Скрытые категории не показываются.
- **«Вернуть в график»** (`POST /order-items/:id/return`, `placeItemOnTeam`): «В очередь (FIFO)» — позиция встаёт на своё место по приоритету и дате передачи, задачи позже по очереди сдвигаются вправо; «На дату» — с выбранного дня, задачи позиции закрепляются, остальные задачи бригады сдвигаются вправо. В обоих случаях задачи других позиций раньше своего дня не встают.
- **Удалить позицию целиком.** В окне задачи галочка «Удалить позицию целиком — все дни (N дн., M шт)» (`DELETE /daily-tasks/:id?whole=1`): снимаются все задачи позиции без факта, дни с фактом не трогаются. «Отменить» восстанавливает удалённые задачи.
- **Перенести позицию целиком.** В окне переноса галочка «Перенести позицию целиком — все дни» (`PUT /daily-tasks/:id` с `wholeItem: true`): все задачи позиции без факта (во всех бригадах) встают с выбранной даты в выбранную бригаду одним куском, закреплённо; освободившееся место — по выбору «Заполнить / Оставить пустым».
- `GET /order-items/:id/plan-summary` — дни и штуки позиции в плане (для галочек).
- **«Отменить» после «Вернуть в график» и переноса позиции целиком.** Перед действием сервер сохраняет снимок плана (`PlanSnapshot`: задачи без факта затронутых бригад с даты действия и самой позиции, её отметка «снято вручную» и пометки «оставлено пустым») и отпечаток состояния сразу после действия. `POST /plan-snapshots/:id/restore` возвращает всё ровно как было; если после действия в этой области что-то меняли, отмена отказывается («После этого график бригады уже меняли…»), чтобы не затереть чужие правки. Снимки старше суток удаляются.
- Бригада для «Вернуть в график» и переноса позиции целиком должна делать товар (норма на товар, а без норм — бригада категории), иначе сервер ничего не трогает и отвечает ошибкой. Если позиция не встала (нет мощности), план бригады возвращается как был. Список бригад в окне — `GET /order-items/:id/teams`: бригады с нормой, а для товаров без норм — бригады категории.

#### Перенос: заполнять ли освободившееся место

- В окне «Перенос задачи» выбор «Освободившееся место»: **Заполнить** (как раньше — следующие задачи бригады сдвигаются раньше и занимают место) или **Оставить пустым** (остальные задачи остаются на своих днях: не готовы полуфабрикаты, бригада нужна под брак и т. п.). Последний выбор запоминается в браузере; «Вернуть» после переноса работает в том же режиме.
- `PUT /daily-tasks/:id` принимает `fill` (по умолчанию `true`). `fill: false`: старая бригада не пересобирается; новая — с нового дня через `replanTeamFrom(..., { keepStarts: true })`: позиция не может встать раньше своего первого дня, поэтому задачи только сдвигаются вправо (если в новом дне не хватило места), пустые дни остаются. В ответе `cascade.filled`.
- **«Оставлено пустым» в ячейке.** Перенос с «Оставить пустым» (одной задачи или всей позиции) запоминает освободившиеся ячейки позиции (`EmptySlot`: позиция, день, бригада, кто, когда). В «Графике» в такой ячейке написано «оставлено пустым», при наведении — кто и когда. Надпись видна, пока в ячейке нет задачи и у бригады в этот день есть свободное место (`GET /daily-tasks/empty-slots` → `stillFree`); если место потом заняли (например, «Перепланировать очередь»), надпись пропадает. Если у позиции в периоде задач не осталось, строка всё равно показывается.
- Проверено на копии прода (Бригада #12): перенос позже — 0 позиций встали раньше, освободившиеся 32 шт остались пустыми; перенос раньше — 0 раньше, 5 сдвинулись вправо; перенос на другую бригаду — план старой бригады не изменился. Количества позиций не меняются.

#### Аналитика загрузки и факт из синка

**Загрузка бригад (`/planning/load-matrix`, `/planning/team-load`, `pages/TeamLoad.tsx`).** Раньше загрузка считалась по мощности категории и показывала 0%. Теперь — как в планировщике: Σ доли бригадо-дня (`loadShare` или штуки / норма бригады × численность), мощность дня с учётом корректировок, выходные и праздники отмечены. Режимы: «Все бригады» (матрица бригада × день), «По бригаде» (позиции × дни: штуки и доля дня, ручные правки 📌), «Перегрузка» (дни, где плана больше мощности), «Недогрузка» (свободное время по рабочим дням). Старые `/planning/overload` и `/planning/underload` удалены.

**Факт из синка (`recordSyncFact` в `/sync/1c`).** Раньше факт = разница остатка «Не обеспечен» из отдельного запроса `ПолучитьФакт()`: он уменьшался и от заказа на производство (переход в «Ожидается к поступлению»), сопоставлялся по коду вместо артикула (из 167 строк совпадало 28), второй синк за день затирал первый — получалось «2412 произведено при остатке 492». Теперь факт = на сколько уменьшился остаток «к обеспечению» позиции между синками, по тем же данным, что и заказы (`ПолучитьЗаказы()`):
- остаток уменьшился → разница в факт за сегодня (МСК), к уже внесённому за день прибавляется;
- позиция пропала из выгрузки активного заказа → весь её остаток в факт, позиция **обнуляется, а не удаляется** (сохраняются её факт и история), будущий автоплан по ней убирается, ручные задачи остаются;
- заказ пропал из выгрузки целиком → остаток всех позиций в факт, позиции обнуляются, заказ в архив;
- заказ вернулся из архива → факта нет (прошлый остаток устаревший);
- **дата факта:** синк до 12:00 МСК — выпуск предыдущего рабочего дня (бухгалтерия проводит выпуск на баланс вечером или утром следующего дня), после 12:00 — сегодняшний. Иначе два синка в день (утро + вечер) клали на один день два дня выпуска: 26.10 вышло 6053 шт против 4233 по акту цеха сборки, а вечерний синк отдельно совпал с актом в 41 строке из 50;
- факт пишется в задачу позиции за день факта, иначе — отдельной строкой на бригаду, у которой позиция в плане. **Бригады в 1С нет** (выпуск ставится на баланс под заказ без бригады) — она «по плану», мастер может поправить в «Плане на день»;
- **защита:** если из выгрузки разом пропало больше 30% активных заказов (и больше 20) — факт за этот синк не пишется, в ответе синка `factGuard` (так выглядел синк из тестовой базы 26.10).
- **Факт не удаляется никогда.** «Очистить график» удаляет только задачи без факта, у задач с фактом обнуляет план (26.10 кнопка стёрла 1620 шт утреннего факта, лежавшего на плановых задачах, — восстановлено из бэкапа). Удаление задачи с фактом убирает только план; перенос задачи с фактом на другую дату переносит только план, факт остаётся на своём дне. Автоматика (перепланирование, каскады, блокировки, перебалансировка) и раньше трогала только задачи без факта. Факт удаляется только вместе с позицией или заказом при их явном удалении.
- Поле `fact` из 1С больше не используется. Это «обеспечено», а не строго «произведено»: резерв со склада тоже уменьшает остаток.

#### Выбор бригады как у Raytec и ручные правки

**Выбор бригады (`autoPlanOrderItem`, `selectEarliestFreeTeam`):** бригада выбирается один раз на позицию, а не каждый день. Берётся та, что раньше освободится: первый рабочий день от старта, где у неё есть свободное время (с учётом корректировок мощности, блокировок категории и уже стоящих задач). В один день — та, у кого меньше занято; ничья — у кого выше мощность по товару, затем по названию. Позиция раскладывается по дням подряд только на этой бригаде. Если у позиции есть ручная задача или начатая работа (факт) на бригаде с нормой — остаток идёт туда же.

**Ручные правки (`DailyTask.manuallyPlaced`) — автоматика их не трогает:**
- Закрепляет задачу любое действие мастера, если что-то реально поменялось: количество, бригада, дата (`PUT /daily-tasks/:id`), добавление задачи (`POST /daily-tasks`), разбивка (обе части), назначение бригады списком (`/daily-tasks/assign-team`).
- Не удаляют и не двигают ручные задачи: «Перепланировать очередь», «Перепланировать» заказа, каскадные сдвиги, «Перебалансировать день». Остаток позиции планируется вокруг ручных задач (`manualPlanOf`: их штуки вычитаются, их дни пропускаются).
- Снять закрепление: `PUT /daily-tasks/:id` с `manuallyPlaced: false`; в «Графике» — кнопка «Снять закрепление» в окне задачи. Закреплённые задачи помечены 📌.
- Исключение: скрытие категории по-прежнему удаляет все её задачи без факта, включая ручные (явное решение убрать категорию из плана).

**Дата передачи по строке (бэк, этап 2):** `OrderItem.transferDate` приходит из синка в каждой позиции (`items[].transferDate`); очередь во всех местах («Перепланировать очередь», «Запланировать незапланированные», вытеснение в каскадах) — по `queueDateMs`: дата строки → дата заказа → сегодня (раньше заказ без даты вставал в начало очереди). Старая версия BSL поле не шлёт — тогда всё как раньше. Дата видна в карточке заказа (колонка «Дата передачи») и помощнику.

**Попутные исправления:**
- «Перепланировать» заказа удаляло все задачи заказа, включая внесённый факт. Теперь удаляет только будущие автоматические.
- «Запланировать» (позиция, заказ) и «Запланировать незапланированные» планировали полное количество поверх уже стоящего плана, получался двойной план. Теперь дописывают только недостающее (`plannedAheadQty`). Позиции заказа планируются по очереди, а не параллельно.

#### Фикс 7: деление позиции по дням как у Raytec (непрерывное время)

**Проблема:** штуки на день считались как `Math.round(свободная доля × мощность)`, а загрузка дня — как `штуки / мощность`. У кольцевых (22,5 шт/день) выходило 23 вместо 22, на стыках позиций ±1 шт.

**Как делает Raytec (восстановлено по его плану от 16.10, 338 позиций):** время бригады непрерывное, позиция занимает `Q / мощность` бригадо-дней. В каждый день идёт целая часть (`floor`), остаток от округлений — в последний день позиции (61 шт при 22,5/день → 22, 22, 17). Следующая позиция стартует с точной точки.

**Исправление:**
- `DailyTask.loadShare Float?` — доля бригадо-дня, которую задача занимает по плану. Нулевая колонка, `db push` без флага.
- `autoPlanOrderItem` делит позицию по правилу Raytec и пишет `loadShare`.
- Загрузка (`calculateTeamLoad`, каскады) — через `taskLoad()`: `loadShare`, иначе `plannedQuantity / мощность`.
- Prisma-расширение сбрасывает `loadShare` в `null`, когда задачу меняют не планировщиком (количество или бригада).

Проверка на копии прода в условиях снимка Raytec (его позиции, бригады, порядок, старт 19.10): совпадение позиций по дням и штукам — 76% с нашими нормами по бригадам, 94% с единой (максимальной) нормой на товар, как у Raytec.

#### Фикс 3: дублирующиеся позиции одного товара в заказе

**Проблема:** если в заказе клиента одна и та же номенклатура встречалась в двух строках ТЧ (напр. 447 + 72 = 519), синк записывал только одну строку, перезаписывая предыдущую. В итоге `OrderItem.quantity = 447` вместо `519`. Raytec показывал 519, Factory Planner — 447.

**Причина:** `INNER JOIN Товары × РаспределениеЗапасов` по `(Номенклатура, Характеристика)` давал картезианское произведение строк — 2 × 2 = 4 строки вместо 1. BSL-группировка суммировала все 4 и получала 1038.

**Исправление (`docs/1c_map.md`, `ПолучитьЗаказы()`):**
- `тов_агр` — подзапрос: Товары сгруппированы по `(Ссылка, Номенклатура, Характеристика)` с фильтрами Отменено/ВариантОбеспечения внутри. Один ряд на пару (заказ, номенклатура).
- `рз_агр` — подзапрос: РаспределениеЗапасов агрегирован с `СУММА(Количество)` по `(ЗаказНаОтгрузку, Номенклатура, Характеристика)`. Один ряд на пару (заказ, номенклатура).
- JOIN теперь 1:1, картезианское произведение невозможно.
- Дополнительно: BSL-группировка `ПозицииМап` оставлена как страховка.

#### Количество людей в бригаде (`headcount`) и пересчёт мощности на человека

**Суть:** мощность продукта теперь хранится **на одного человека** в день, а не на бригаду. Реальная ёмкость бригады = `capacityPerDay × team.headcount`.

**Что изменилось:**

- **Схема**: `Team.headcount Int @default(1)` — новое поле. Источник: `КоличествоРабочихЦентров` из `Справочник.ВидыРабочихЦентров` в 1С.
- **BSL `ПолучитьБригады()`**: добавлен `КолРЦ` в SELECT и структуру; поле `headcount` передаётся в синк-объект как `КоличествоРабочихЦентров`.
- **BSL `ПолучитьCapacity()`**: убрано деление на `КолРЦ` из формулы — `МинутНаЕдиницу = ВремяРаботы / (Загрузка × КолУп)`. Результат = производительность одного человека.
- **Бэкенд**: `POST /sync/1c` — upsert бригады сохраняет `headcount`; `PUT /teams/:id` — принимает `headcount` (положительное целое); `calculateTeamLoad` и `autoPlanOrderItem` умножают `capacityPerDay` на `team.headcount` при всех расчётах нагрузки и планировании.
- **Планировщик**: `cascadeShiftLeft` и `cascadeShiftRight` также используют `effectiveCapacity = capacityPerDay × headcount`.
- **UI (страница «Бригады»)**: поле «Количество людей» в форме, колонка «Людей» в таблице.
- **UI (страница «Товары»)**: колонка переименована в «Произв. на чел./день».

**Обновление headcount:** при изменении `КоличествоРабочихЦентров` в 1С — обновляется при следующем синке автоматически. Можно изменить и вручную через страницу «Бригады».

#### Фикс синка заказов: 25 вместо ~290 активных заказов

**Симптом:** после перехода на `РаспределениеЗапасов` в синк попадали только 25 заказов из ~290.

**Причина:** фильтр `РЗ.СостояниеЗапаса = НеОбеспечен` в `ПолучитьЗаказы()` слишком жёсткий. Большинство позиций активных заказов находятся в состоянии `ОжидаетсяКПоступлению` или `НаСогласованииПоставки` — при INNER JOIN они не попадали в выборку, и весь заказ выпадал. `НеОбеспечен` — лишь одно из восьми значений перечисления `СостоянияЗапаса`.

**Исправление (BSL):** фильтр расширен с одного значения до трёх:
```
РЗ.СостояниеЗапаса В (НеОбеспечен, ОжидаетсяКПоступлению, НаСогласованииПоставки)
```
Эти три состояния означают «нужно произвести / ещё не готово». Остальные пять (`ВНаличии`, `ВНаличииОжидаетсяРазблокировка` и др.) — товар уже есть на складе.

#### Факт-записи в графике и дата «Готово по плану»

**Ожидаемое поведение:** когда синк из 1С приходит, для каждой позиции с реальным выпуском (delta НеОбеспечен > 0) создаётся `DailyTask` с `plannedQuantity=0, actualQuantity=delta` на сегодня. В графике такая запись отображается зелёным ✓. Когда затем запускается «Запланировать незапланированные» — планирование начинается с завтра. Итог: сегодня виден факт, завтра и дальше — план. Это корректная логика.

**Два реальных бага:**

**Баг 1:** факт-синк создавал `DailyTask` с `actualQuantity=0` когда дельта = 0 (ничего не произведено). Эти пустые записи засоряли график.
→ Фикс: `if (todayDelta <= 0) continue` — запись не создаётся при нулевой дельте.

**Баг 2:** `/planning/orders-completion` брал любой `DailyTask` (включая факт-записи с `plannedQuantity=0`) для расчёта `expectedCompletionDate`. Это давало ложную дату «Готово по плану» у незапланированных заказов.
→ Фикс: фильтр `where: { plannedQuantity: { gt: 0 } }` — дата считается только по реальным плановым задачам.

**Примечание:** «Запланировать незапланированные» правильно игнорирует факт-записи — формула `done` считает только задачи с `plannedQuantity > 0 AND actualQuantity IS NOT NULL`.

#### Фикс планировщика: «Запланировать незапланированные» пропускал ~95% позиций

**Симптом:** нажатие «Запланировать незапланированные» планировало лишь ~25 из 370+ позиций цеха.

**Причина:** `POST /order-items/plan-unplanned` считал позицию «выполненной», если сумма `actualQuantity` по всем её `DailyTask` ≥ количества. Факт-синк из 1С записывал `Зарезервировано` как `actualQuantity` при `plannedQuantity = 0`. В 1С `Зарезервировано` — системный резерв, выставляемый автоматически при проведении заказа, а не физически произведённый товар. Итог: 333 из 372 позиций имели `actualQuantity = полное количество` → планировщик считал их сделанными.

**Исправление (`src/index.ts`, `/order-items/plan-unplanned`):** изменена формула `done`:
- **Было:** `sum(actualQuantity)` по всем задачам — включая факт-синк (plannedQuantity = 0)
- **Стало:** `sum(actualQuantity)` только по задачам с `plannedQuantity > 0 AND actualQuantity IS NOT NULL` (явно запланировано и подтверждено фактом)

**Логика как у Raytec APS:** Raytec планирует только `Обеспечено + НеОбеспечено` и не считает `Зарезервировано` произведённым товаром.

#### Фикс синка бригад: альтернативные ВРЦ не попадали в план

**Симптом:** категория "СВЕТИЛЬНИКИ AVRORA, OPERLUX, UNIVERSAL" тянула только одну бригаду, хотя в спецификации их две (Бригада #6 + Бригада #7).

**Причина:** `ПолучитьСвязкиБригадНоменклатура()` читала только `ЭтапыПроизводства.ВидыРабочихЦентров` (основную ТЧ). Альтернативные бригады в 1С хранятся в отдельной ТЧ `АльтернативныеВидыРабочихЦентров` — в UI они отображаются вложенными под основную строку, заголовок секции показывает `(1)` (одна основная строка), а альтернативные идут отступом ниже.

**Исправление (BSL):** добавлен `ОБЪЕДИНИТЬ` со вторым запросом по `Справочник.ЭтапыПроизводства.АльтернативныеВидыРабочихЦентров`. После синка все альтернативные бригады подтягиваются в `CategoryTeam` наравне с основными.

**Примечание:** в 1С синтаксис `ОБЪЕДИНИТЬ РАЗЛИЧНЫЕ` не существует — нужно `ОБЪЕДИНИТЬ`, дубли убирает `ВЫБРАТЬ РАЗЛИЧНЫЕ` в каждой части.

#### Двунаправленный каскад и защита ручных переносов

- **`DailyTask.manuallyPlaced`** — новое поле `Boolean @default(false)`. Выставляется в `true` при явном переносе задачи через `PUT /daily-tasks/:id`. Задача с этим флагом не трогается ни `cascadeShiftLeft`, ни `cascadeShiftRight`.
- **`cascadeShiftLeft`** (новая функция): при переносе задачи вправо — после компактации позиции бригада подтягивает задачи из следующего рабочего дня в образовавшийся свободный слот. FIFO: задачи с ранним `approvedAt` заполняют слот первыми. Рекурсия до 60 итераций.
- **`cascadeShiftRight`** (обновлено): теперь пропускает задачи с `manuallyPlaced = true`. FIFO: задачи с поздним `approvedAt` вытесняются первыми (ранние идут раньше в очереди).
- **`compactOrderItem(orderItemId, preserveDate?)`** (исправлен): при передаче `preserveDate` — задача на этой дате сохраняется, её количество вычитается из того, что нужно переспланировать. Раньше функция удаляла задачу, которую пользователь только что поставил вручную.
- Оба каскада запускаются через `setImmediate` — ответ API возвращается немедленно, реструктуризация идёт фоном.
- Задачи с `actualQuantity != null` (есть факт) не сдвигаются никогда.
- **Приоритет — исключительно FIFO по `approvedAt`** (дата согласования из 1С).

#### Блокировки категорий (`CategoryBlock`)

- **Новая модель** `CategoryBlock`: `categoryId`, `companyId`, `startDate`, `endDate`, `reason?`. Связи: `ProductCategory.blocks[]`, `Company.categoryBlocks[]`.
- **`autoPlanOrderItem`** теперь проверяет CategoryBlock на каждую дату — заблокированные даты пропускаются так же, как выходные.
- **`POST /categories/:id/blocks`** с `cascadeTasks=true` — задачи из периода блокировки удаляются, их суммы по `orderItemId` складываются на первый рабочий день после конца блока, затем `cascadeShiftRight` разряжает перегруз.
- **UI «Блоки»** на странице «Категории» — кнопка рядом с «Бригады». Модальное окно: список активных блоков (период + причина + кнопка «Снять»), форма создания (даты, причина, чекбокс «Перераспределить задачи»).

- **Связь бригада↔категория** — `ПолучитьСвязкиБригадНоменклатура()`: `РесурсныеСпецификации.ОсновноеИзделиеЭтап` → `ЭтапыПроизводства.ВидыРабочихЦентров`; подтверждено на реальных данных
- **Категории = пк_-продуктовые линейки** — `capacityPerTeamPerDay` устанавливается из 1С автоматически
- **Мощность на продукт (авг 2026)** — `Product.capacityPerDay` из маршрутизации: изначально `⌊480 / (ВремяРаботы / Загрузка / КолУпаковок)⌋`; в сентябре 2026 формула скорректирована — `КоличествоРабочихЦентров` убрано из знаменателя, значение теперь означает производительность **одного человека** (см. раздел сентябрь 2026); в октябре 2026 добавлена `ProductTeamCapacity` — мощность по бригадам (см. раздел октябрь 2026). 588 продуктов получили значения из реальных операционных норм, как у Raytec APS. Планировщик использует `ProductTeamCapacity ?? product.capacityPerDay ?? category.capacityPerTeamPerDay`
- **Авторизация** — JWT в httpOnly cookie; регистрация с ИНН компании; первый пользователь = ADMIN
- **Рабочий календарь** — пропуск субботы, воскресенья и 14 российских праздников
