# Factory Planner — планирование производства

B2B SaaS-приложение для планирования производства. Несколько компаний, каждая со своими данными.

**Содержание:** [Контекст](#контекст-и-цели) · [Модель данных](#модель-данных) · [Разработка](#разработка) · [Деплой](#деплой) · [API](#api) · [Интеграция с 1С](#интеграция-с-1с) · [История изменений](#история-изменений)

---

## Контекст и цели

**Задача:** заменить ручной обмен Excel-файлами между офисом и производством на единую веб-систему.

**Пользователи:**
- **Руководитель (ADMIN)** — первый зарегистрированный в компании пользователь. Подтверждает заявки коллег на доступ, управляет токеном синхронизации с 1С.
- **Планировщик** — загрузка заказов из 1С, формирование и корректировка плана, сводка факта.
- **Начальник цеха** — распределение бригад, ввод фактического выпуска и комментариев.

**Проблемы текущего процесса:** ручной обмен файлами, риск рассинхронизации, дублирование данных, нет единого источника правды.

## Модель данных

| Сущность | Описание |
|----------|----------|
| **Company** | Компания: ИНН, название, `syncToken` (токен для 1С). Единица изоляции данных. |
| **User** | Пользователь: email, пароль (bcrypt), роль (ADMIN/MEMBER), статус (PENDING/APPROVED/REJECTED). |
| **Workshop** | Участок/цех. Группировка категорий. |
| **ProductCategory** | Категория номенклатуры (= пк_-продуктовая линейка). `capacityPerTeamPerDay` устанавливается из 1С при синке. |
| **Product** | Номенклатура: код, название, категория, мощность в сутки (`capacityPerDay`), флаг ручной блокировки (`capacityLocked`). |
| **Team** | Бригада. Привязывается к категориям через CategoryTeam. |
| **TeamDayCapacity** | Корректировка мощности бригады на конкретный день (фактор 0.0–1.0, причина). |
| **Order** | Заказ клиента: GUID из 1С (`orderRef`), номер (для отображения), клиент, срок, менеджер, флаг `active`. |
| **OrderItem** | Позиция заказа: товар, количество К (к обеспечению). |
| **DailyTask** | Задача на день: позиция + дата + план + факт + комментарий. Флаг `manuallyPlaced` защищает ручные переносы от автоматических каскадов. |
| **CategoryBlock** | Блокировка производства категории на период (нет запчастей, плановый простой). |

### Мультитенантность

Каждая компания полностью изолирована. `Workshop`, `ProductCategory`, `Team`, `Product`, `Order` имеют `companyId`. Уникальные ключи составные: `[name, companyId]`, `[code, companyId]`, `[orderRef, companyId]`. Авторизованные запросы автоматически фильтруются по компании текущего пользователя.

### Ключевые связи

- `Company` → `User[]`, `Workshop[]`, `Team[]`, `ProductCategory[]`, `Product[]`, `Order[]`
- `ProductCategory` ↔ `Team` — many-to-many через `CategoryTeam`
- `Order` → `OrderItem[]`
- `OrderItem` → `DailyTask[]`
- `DailyTask` → `OrderItem`, `Team`, дата
- `Team` → `TeamDayCapacity[]`

### Модель нагрузки бригады

Нагрузка считается в долях бригадо-дня: `load = Σ(plannedQuantity / capacityPerDay)` по всем задачам бригады за день.

- `load = 1.0` — полный рабочий день
- `load > 1.0` — перегруз
- `TeamDayCapacity.factor` — доступная доля дня (например, `0.7` = вышло 7 из 10 человек)

`capacityPerDay` берётся с уровня **продукта** (`Product.capacityPerDay`). Источник: `ЭтапыПроизводства.ВидыРабочихЦентров.ВремяРаботы` — маршрутизация 1С, как у Raytec APS. Fallback — `ProductCategory.capacityPerTeamPerDay` (ручной ввод в UI).

Если `Product.capacityLocked = true` — поле защищено от перезаписи при синке: значение устанавливается вручную через UI и сохраняется навсегда, пока пользователь явно не нажмёт «Сбросить».

## Авторизация

- Первый зарегистрировавшийся пользователь в компании (по ИНН) получает роль **ADMIN** и сразу входит.
- Последующие регистрации создают заявку **PENDING** — ADMIN видит их на странице «Администрирование» и подтверждает.
- Данные **полностью изолированы** по компании. Пользователь другой компании не видит ни заказов, ни бригад, ни графика чужой компании.
- Сессия — `httpOnly` cookie (JWT, срок 30 дней).

## Интерфейс

### Справочники

- **Участки** — CRUD цехов/участков
- **Категории** — CRUD категорий с мощностью; кнопка «Бригады» для привязки бригад к категории; кнопка «Блоки» для управления блокировками производства на период
- **Товары** — CRUD номенклатуры
- **Бригады** — две вкладки:
  - **Список бригад** — CRUD
  - **Мощности по дням** — сетка-календарь на 2 недели; клик на ячейку задаёт фактор мощности и причину

### Заказы

Две вкладки:
- **Актуальные** — заказы, где факт выпуска ещё не подтверждён по всем позициям. Колонки «Срок договора» и «Готово по плану» (прогноз по текущим задачам, красный если позже срока)
- **Архив** — заказы, где факт выпуска подтверждён по всем позициям

### График (главный экран работы)

Гант-таблица: строки — позиции заказов, колонки — даты.

| Ячейка | Действие |
|--------|----------|
| Пустая | Создать задачу на эту дату |
| Заполненная | Попап: редактировать количество и бригаду |
| Попап → «Перенести →» | Жёлтый баннер, кликни нужную пустую ячейку |
| Попап → «Разбить ÷» | Форма: сколько перенести + на какую дату |

В шапке колонок — цветная полоска нагрузки (зелёный/жёлтый/красный).

### График (главный экран работы) — кнопки планирования

В шапке страницы «График» кнопки действий:

| Кнопка | Действие |
|--------|----------|
| **Запланировать незапланированные** | Автоматически планирует все позиции без плана, начиная с завтра |
| **Перепланировать очередь** | Удаляет весь незапущенный план и пересчитывает с нуля по приоритету (дата согласования) |
| **Категории без бригад** | Показывает список категорий без назначенной бригады с возможностью назначить прямо здесь |
| **↓ Скачать Excel** | Открывает панель выбора периода; скачивает план в .xlsx с двумя листами: детальный и сводка по дням |

### Автоматическое перепланирование при ручном переносе задач

При изменении даты задачи через попап (перенос, разбивка, перемещение) запускается автоматическая двунаправленная корректировка очереди:

| Ситуация | Поведение |
|----------|-----------|
| Задача перенесена **на позднюю дату** | 1. Все незавершённые задачи этой позиции заказа пересчитываются — план позиции «сжимается влево». 2. Следом запускается `cascadeShiftLeft`: бригада тянет задачи из следующего рабочего дня в образовавшийся свободный слот (FIFO по `approvedAt`), рекурсивно до 60 итераций. |
| Задача перенесена **на раннюю дату** | Если бригада перегружена в этот день — задачи с наименьшим приоритетом (поздний `approvedAt`) вытесняются на следующий рабочий день (`cascadeShiftRight`), каскадно до 60 итераций. |

**Защита ручных переносов** — флаг `DailyTask.manuallyPlaced = true` выставляется при явном переносе через API. Задачи с этим флагом не трогают оба каскада (`cascadeShiftLeft` и `cascadeShiftRight`). Задачи с `actualQuantity != null` (есть факт) никогда не сдвигаются.

**Приоритет очереди** — исключительно FIFO по `approvedAt` (дата согласования заказа). `dueDate` не используется в алгоритмах планирования.

### Блокировки категорий

Когда производство категории невозможно на период (нет запчастей, плановый простой, отпуск цеха) — создаётся `CategoryBlock`.

- **Планировщик автоматически пропускает заблокированные даты** — `autoPlanOrderItem` обходит даты, попадающие в любой активный блок категории.
- **Каскад при создании блока** — опция «Перераспределить задачи из периода» (`cascadeTasks=true`): задачи из периода блокировки удаляются и складываются на первый рабочий день после конца блока, после чего запускается `cascadeShiftRight` чтобы разрядить перегруз.
- **UI** — на странице «Категории» кнопка «Блоки» открывает модальное окно со списком активных блоков (чипы: период + причина) и формой создания нового блока (даты, причина, чекбокс каскада). Снять блок можно кнопкой «Снять» на каждом чипе.

### Страница «Товары»

- **Колонка «Производ./день»** — показывает `capacityPerDay` из маршрутизации 1С; иконка 🔒 означает ручную блокировку (синк не перезапишет)
- **Редактирование производительности** — поле в форме «Изменить»; при сохранении ненулевого значения автоматически блокируется
- **Кнопка «Сбросить»** — снимает блокировку; следующий синк с 1С перепишет значение из маршрутизации
- **Поиск** — фильтрация по коду или названию прямо в таблице

### Аналитика и планирование

Вкладки страницы «Аналитика»:

- **Загрузка бригады** — матрица категория × дата; внутри кнопки-переключатели:
  - **По бригаде** — тепловая карта загрузки категорий выбранной бригады
  - **Перегруженные** — задачи, запланированные позже срока поставки (красный бейдж с количеством)
  - **Недогруженные** — бригады с загрузкой < 100% бригадо-дня
- **Завершение заказов** — прогноз дат завершения, процент выполнения
- **Факт за день** — сводка выпуска по бригадам и категориям за выбранный день
- **Незапланированный факт** — позиции, по которым зафиксирован выпуск без плана

### Администрирование (только ADMIN)

Страница `/admin/approvals`. Два блока:

**Синхронизация с 1С** — токен компании для расширения 1С. Кнопки: Показать / Скрыть, Скопировать, Перегенерировать (инвалидирует старый токен).

**Заявки на доступ** — список пользователей со статусом PENDING, кнопки «Разрешить» / «Отклонить».

## Интеграция с 1С

**Платформа:** 1С:ERP Управление предприятием 2, версия 8.3.27.1936

### Стратегия

- Расширение 1С (`ФабрикаПланнер`) **push-ит данные** на `POST /sync/1c`
- Аутентификация — Bearer-токен компании: `Authorization: Bearer <syncToken>`
- Токен хранится в БД (`Company.syncToken`), генерируется при регистрации компании
- ADMIN видит и копирует токен на странице **«Администрирование»** → «Синхронизация с 1С»

### Настройка интеграции (пошагово)

1. Зарегистрировать компанию и войти как ADMIN
2. Перейти в **Администрирование** → нажать «Показать» → скопировать токен
3. Открыть в 1С расширение **ФабрикаПланнер** → Настройки → вставить токен в поле «Токен»
4. Нажать кнопку «Отправить в Factory Planner» — данные синхронизируются

При компрометации токена — нажать «Перегенерировать» и обновить настройки в 1С.

## История изменений

### [текущая] — август 2026 (вторая половина)

#### Ручное управление производительностью

- **`Product.capacityLocked`** — новое поле `Boolean @default(false)` в схеме. Когда `true` — синк из 1С пропускает продукт при обновлении `capacityPerDay`
- **`PUT /products/:id`** — принимает `capacityPerDay: number` (автоматически выставляет `capacityLocked=true`) и `capacityLocked: false` (явный сброс блокировки)
- **Страница «Товары»** — добавлена колонка с мощностью и иконкой 🔒 для заблокированных, кнопка «Сбросить» для разблокировки, поле производительности в форме редактирования, фильтр поиска

#### Экспорт плана в Excel

- **`GET /planning/export-excel?from=&to=`** — возвращает `.xlsx` файл. Лист 1 «Детальный план»: строка = задача (дата, бригада, номер заказа, клиент, срок, артикул, товар, категория, план, факт). Лист 2 «Сводка по дням»: дата + суммарный план + суммарный факт
- **Кнопка «↓ Скачать Excel»** на странице «График» — разворачивает панель с выбором периода; скачивание через `fetch` + `blob` (авторизационные куки автоматически)

#### Двунаправленный каскад и защита ручных переносов

- **`DailyTask.manuallyPlaced`** — новое поле `Boolean @default(false)`. Выставляется в `true` при явном переносе задачи через `PUT /daily-tasks/:id`. Задача с этим флагом не трогается ни `cascadeShiftLeft`, ни `cascadeShiftRight`.
- **`cascadeShiftLeft`** (новая функция): при переносе задачи вправо — после компактации позиции бригада подтягивает задачи из следующего рабочего дня в образовавшийся свободный слот. FIFO: задачи с ранним `approvedAt` заполняют слот первыми. Рекурсия до 60 итераций.
- **`cascadeShiftRight`** (обновлено): теперь пропускает задачи с `manuallyPlaced = true`. FIFO: задачи с поздним `approvedAt` вытесняются первыми (ранние идут раньше в очереди).
- **`compactOrderItem(orderItemId, preserveDate?)`** (исправлен): при передаче `preserveDate` — задача на этой дате сохраняется, её количество вычитается из того, что нужно переспланировать. Раньше функция удаляла задачу, которую пользователь только что поставил вручную.
- Оба каскада запускаются через `setImmediate` — ответ API возвращается немедленно, реструктуризация идёт фоном.
- Задачи с `actualQuantity != null` (есть факт) не сдвигаются никогда.
- **Приоритет — исключительно FIFO по `approvedAt`**. `dueDate` нигде в алгоритмах планирования не используется.

#### Блокировки категорий (`CategoryBlock`)

- **Новая модель** `CategoryBlock`: `categoryId`, `companyId`, `startDate`, `endDate`, `reason?`. Связи: `ProductCategory.blocks[]`, `Company.categoryBlocks[]`.
- **`autoPlanOrderItem`** теперь проверяет CategoryBlock на каждую дату — заблокированные даты пропускаются так же, как выходные.
- **`POST /categories/:id/blocks`** с `cascadeTasks=true` — задачи из периода блокировки удаляются, их суммы по `orderItemId` складываются на первый рабочий день после конца блока, затем `cascadeShiftRight` разряжает перегруз.
- **UI «Блоки»** на странице «Категории» — кнопка рядом с «Бригады». Модальное окно: список активных блоков (период + причина + кнопка «Снять»), форма создания (даты, причина, чекбокс «Перераспределить задачи»).

### [август 2026 — первая половина]

#### Исправления инфраструктуры

- **Схема Prisma приведена в соответствие с миграциями** — `schema.prisma` не содержал полей `companyId`, `active`, `orderRef` на `Order`, `companyId` на `Workshop`/`Team`/`ProductCategory`/`Product`, `capacityPerDay` на `Product`, `syncToken` на `Company`. Схема обновлена, Prisma Client перегенерирован. До этого TypeScript-сборка падала с ~15 ошибками.
- **Фикс поля сортировки в `plan-unplanned`** — `orderBy: { order: { createdAt: "asc" } }` заменено на `orderBy: { order: { approvedAt: "asc" } }`: модель `Order` не имеет `createdAt`, FIFO-сортировка теперь по дате согласования заказа.
- **Добавлен `import { randomUUID } from "crypto"`** — функция создания компании (`POST /auth/register`) вызывала `randomUUID()` без импорта; добавлен top-level импорт.
- **Обнаружен и устранён баг «два сервера»** — в фоне висел `ts-node src/index.ts` (старая версия), занимавший порт 3000. Все запросы шли к нему, а не к `node dist/index.js`. Старый сервер использовал устаревшую Prisma-схему без поля `active`, из-за чего планировал все 1329 позиций (включая неактивные заказы) и создавал задачи с датами 2025 года (seed-данные накладывались на новые задачи). Сервер убит, рабочим является только `node dist/index.js`.

#### Фильтрация заказов через `РаспределениеЗапасов`

- **BSL `ПолучитьЗаказы()` переписан** — вместо прямой выборки из `ЗаказКлиента.Товары` используется `ВНУТРЕННЕЕ СОЕДИНЕНИЕ РегистрСведений.РаспределениеЗапасов`. Количество = `Обеспечено + НеОбеспечено`.
- **Исключение «Готов к закрытию»** — фильтр по `тов.ВариантОбеспечения НЕ В (Отгрузить, СоСклада, НеТребуется, ПереданРанее)` убирает позиции, которые уже отгружены или переданы. Количество активных заказов снизилось с 459 до 287.
- **Исключение закрытых и несогласованных** — фильтр по `РЗ.Состояние В (Обеспечить, ОбеспеченКДате, ОжидаетсяПоНеподтвержденномуЗаказу)`.
- **Семантика `Обеспечено + НеОбеспечено`** — это правильная формула спроса: `Обеспечено` = есть заказ на производство, но товар ещё не произведён/не отгружен; `НеОбеспечено` = заказа на производство ещё нет. По мере производства и отгрузки `ВариантОбеспечения` меняется и строки выпадают из регистра — система самоочищается.
- **Убраны лишние поля** — все ссылочные типы (справочники) заменены на `.Наименование` строки; `ЕСТЬNULL(..., "")` на всех nullable-полях; убрано использование `НоменклатураГруппа` из `ДополнительныеРеквизиты` (вызывало ошибку `Значение содержит данные недопустимых типов`).

#### Верификация данных (сравнение с Raytec APS)

Raytec APS — внешняя APS-система, используемая на производстве. Для понимания расхождений были изучены BSL-функции их интеграционного модуля (`риаВыгрузкаВRaytecAPS`).

**Что проверено:**

## Сравнение с Raytec APS — план дальнейших шагов

Цель: убедиться, что наш алгоритм планирования даёт бизнесово правильный результат — те же заказы, те же объёмы, разумные даты.

### Что есть сейчас

| | Наша система | Raytec |
|---|---|---|
| Дата отчёта | 10.08.2026 (живые данные) | 31.07.2026 (снимок) |
| Горизонт | Авг–Окт 2026 | неизвестно из отчёта |
| Заказов | 287 активных | 244 в отчёте |
| Формула спроса | `Обеспечено + НеОбеспечено` | то же |

### Шаг 1. Выровнять базу данных

Текущая БД — снимок на 31.07.2026, но планирование запускается от 11.08.2026. Для честного сравнения с Raytec-отчётом нужно либо:
- **Вариант А** — использовать текущие данные как есть и сравнивать итоговые объёмы по категориям (без привязки к датам)
- **Вариант Б** — запустить `plan-unplanned` с `startDate = 2026-08-01` (дата Raytec-отчёта) через API `/order-items/:id/auto-plan` с параметром `startDate`

Рекомендую **Вариант А**: сначала убедиться что категориальные объёмы совпадают, потом разбираться с датами.

### Шаг 2. Загрузить Raytec-отчёт в сравнимый формат

Raytec-отчёт `Отчет_31_07_2026.xlsx` нужно привести к таблице:
```
category | order_number | quantity_planned
```

Если в отчёте есть даты — добавить дату. Задача: сопоставить построчно с нашей таблицей `DailyTask`.

### Шаг 3. Сравнить объёмы по категориям

```sql
SELECT pc.name, SUM(oi.quantity) as our_demand
FROM OrderItem oi JOIN Product p ... JOIN ProductCategory pc ...
JOIN "Order" o WHERE o.active=1
GROUP BY pc.name ORDER BY our_demand DESC;
```

Сравнить с агрегатами из Raytec-отчёта по категориям. Ожидаемые расхождения:
- **13 заказов с несовпадением категорий** (ПАНЕЛИ SPARTA, КОРПУСА SLIM) — нужно починить маппинг названий категорий в BSL
- **18 новых заказов после 31.07** — их у Raytec нет

### Шаг 4. Починить категории с несоответствием названий

В 1С некоторые позиции имеют `пк_ВидДляРасчетаГрафикаПроизводства` с названием, не совпадающим с тем, что в нашей БД. Нужно:
1. Найти конкретные заказы с расхождением (из шага 3)
2. Проверить в 1С как называется категория у этих номенклатур
3. Либо исправить название категории в нашей БД, либо добавить алиас в BSL

### Шаг 5. Проверить мощности категорий

Для категорий с большими объёмами проверить совпадение:
- `ProductCategory.capacityPerTeamPerDay` в нашей БД
- Производительность в Raytec (в отчёте или в их настройках)

Подозрение: Raytec мог использовать другие значения мощности, из-за чего их план растянут/сжат иначе.

### Шаг 6. Сравнить список заказов и очерёдность

Raytec планирует по приоритету (`Demand_Priority` или `dueDate`). Наш алгоритм сортирует по `approvedAt`. Нужно проверить:
- Raytec использует `ДатаОтгрузки` (dueDate) как приоритет или что-то другое?
